记录实现过程中实际用到的技术、踩到的坑和做出的取舍，按类别整理。只记**已经验证过**的内容；没验证的写明"未验证"。

## 2. 执行引擎（k6）

| 主题 | 内容 | 日期 |
|---|---|---|
| 数据驱动的通用脚本 | 业务流程是页面上维护的数据，不是手写代码。`perf/runner.js` 在 init 阶段用 `open(__ENV.PLAN_FILE)` 读 plan.json 解释执行。k6 要求 scenario 的 `exec` 指向导出的函数名，所以只导出一个函数 `runFlow`，内部用 `exec.scenario.name` 找到对应的流程 | 2026-09-30 |
| `open()` 的路径 | 相对路径是相对脚本所在目录，所以 `PLAN_FILE` 必须用绝对路径 | 2026-09-30 |
| **实时仪表盘会阻止 k6 退出** | 只要有浏览器连着 web dashboard（`:5665`），k6 跑完后就一直等页面关闭，不写 summary、不退出。联调时运行因此卡在"运行中"。处理：仪表盘只监听 `127.0.0.1`，页面上不嵌入也不链接它；运行中的进度由后端从 `k6.log` 取最新一行；结束后的图表用导出的 `dashboard.html` | 2026-09-30 |
| 仪表盘导出 HTML | `K6_WEB_DASHBOARD=true` 加 `K6_WEB_DASHBOARD_EXPORT=<路径>` 导出静态报告。聚合周期默认 10 秒，短运行会因为数据点不够而跳过导出；加 `K6_WEB_DASHBOARD_PERIOD=1s` 后 3–10 秒的运行都能导出（约 166 KB） | 2026-09-30 |
| `handleSummary` 的数据结构 | k6 v2.3.0 默认仍是旧结构：顶层 `metrics`、`root_group`、`options`、`state`；`metrics[名称]` 为 `{type, contains, values, thresholds?}`。新的机器可读结构要显式加 `--new-machine-readable-summary`（未实测）。研究阶段"v2 可能默认启用新结构"的推测不成立 | 2026-09-30 |
| 分步骤指标 | 子指标（如 `http_req_duration{step:f1s1}`）只有被阈值引用才会出现在 summary 里。给每个步骤加占位阈值 `max>=0`（trend）和 `rate>=0`（rate），没有样本时也判为通过。占位阈值不计入判定 | 2026-09-30 |
| 没有样本时的取值 | 没有样本的子指标在 summary 里各项都是 0 而不是缺失。为避免把"没发请求"显示成"0 毫秒"，Run Record 里统一改成 `null` | 2026-09-30 |
| `http_req_failed` 的 passes / fails | `passes` 是"失败的请求数"，`fails` 是"没失败的请求数"，容易看反。每步请求数取两者之和 | 2026-09-30 |
| 期望状态码 | 用 `responseCallback: http.expectedStatuses(...)` 让 `http_req_failed` 按期望状态码判断（期望 404 的请求不算失败）。回调对重定向的每一跳都生效，所以把 301 / 302 / 303 / 307 / 308 也算作符合预期，最终状态码由 check 把关（重定向这一点依据文档，未实测） | 2026-09-30 |
| `dropped_iterations` | 加了阈值后，即使一次都没丢也会出现在 summary 里，`count==0` 判为通过。open 模型下作为有效性检查 | 2026-09-30 |
| 到达率必须是整数 | 小数到达率用 `timeUnit` 换算，例如每秒 0.7 次写成每 10 秒 7 次。`maxVUs` 等于 `preAllocatedVUs`，不自动扩容，VU 不够时由有效性阈值暴露 | 2026-09-30 |
| `name` tag | 请求的 `name` tag 用 `方法 路径模板`（带 `{{变量}}` 的原文），避免每个不同的 URL 产生一条时间序列。设置 `name` 后 `url` tag 也变成同一个值 | 2026-09-30 |
| 退出码 | 0 = 阈值全过；99 = 有阈值未过（未达标和测试无效都是 99，要靠 `run-record.json` 的 `k6Verdict` 区分）；107 = plan 无效或脚本异常，没有 `run-record.json`；被 SIGINT 中断为 105 或被信号结束 | 2026-09-30 |
| `k6 inspect` | 不发请求就能看到生成的 options，适合检查 plan 能否被引擎接受 | 2026-09-30 |
| 失败时不空转 | 某一步 check 没通过时，本次迭代的后续步骤不再执行，但仍然等待 think time，避免失败后循环变快、流量意外变大 | 2026-09-30 |
| 百度首页的特点 | 首页 `/` 返回 200 且包含"百度"；搜索路径 `/s` 会 302 到验证码页（`baseUrl` 以外的主机），不能用作示例 | 2026-09-30 |
| 调试模式复用解释器 | plan 带 `debug` 段时，`compileStep` 强制 `responseType: 'text'`、`thinkSec: 0`；`runStep` 把每个 check 函数包一层记录单条结果（`check()` 只返回总的布尔值）；记录 push 进 trace。压测路径的代码不变 | 2026-10-09 |
| `handleSummary` 看不到 VU 的变量 | k6 在独立的运行时里执行 `handleSummary`，VU 里给模块变量赋的值它看不到；VU 也不能写文件。调试记录改为迭代结束时 `console.log` 一行 JSON，用 `--console-output=<文件>` 单独落盘、`--log-format=json` 让每行是 `{level, msg, source, time}`，后端取 `msg` 再解析一次。实测带 64 KB 响应体的一行也完整 | 2026-10-09 |
| 调试的 k6 参数 | `--no-thresholds` 不评估阈值（退出码恒为 0，107 仍表示 init 阶段异常）；`--quiet` 去掉进度条；`--no-usage-report` 省掉结束时的匿名统计上报；`K6_WEB_DASHBOARD=false` 不开仪表盘。1 次请求的调试从启动到退出约 65 ms（本机目标）到 600 ms（百度，含 TLS） | 2026-10-09 |
| 连接被拒时 k6 给的响应 | `status` 0、`body` 空、`timings` 全 0、`error` 为 `dial: connection refused`、`error_code` 1212，不抛异常。状态码检查不通过，所以调试里是 `failed`（带 error 文字）而不是 `error` | 2026-10-09 |
| 什么会让脚本抛异常 | 路径里有空格时 k6 自动编码后照发（目标返回 404），不抛；真正抛的是 init 阶段 `new RegExp` 编译提取规则里写错的正则（`SyntaxError: Unterminated group`），k6 以 107 退出、没有任何记录。所以后端对 107 的提示直接点名"正则写错" | 2026-10-09 |

## 3. 后端

| 主题 | 内容 | 日期 |
|---|---|---|
| 后端框架 | Python 3.12 + FastAPI 0.142 + uvicorn 0.54（由 `uv add` 安装，版本锁在 `uv.lock`）。只能单进程运行，不要加 `--workers`（k6 进程句柄在内存里） | 2026-09-30 |
| SQLite | 用 Python 标准库 `sqlite3`。不共享连接，每次操作新建、用完关闭；开 WAL 和 10 秒 busy timeout。`with sqlite3.connect()` 只提交不关闭，所以自己包了提交 / 回滚 / 关闭的上下文管理器 | 2026-09-30 |
| 主键不复用 | 主键用 AUTOINCREMENT，删除后 id 不复用，历史运行里的 `testId` 不会指向别的测试 | 2026-09-30 |
| 种子数据只写一次 | 用 `PRAGMA user_version` 标记是否建过库：为 0 且定义表全空才写种子，用户删光数据后重启不会被重新灌入 | 2026-09-30 |
| 运行快照 | 发起运行时把测试、流程、接口、负载配置、环境展开成一份自包含的 plan 存库，之后修改或删除定义不影响历史运行 | 2026-09-30 |
| 统一错误格式 | 重写 FastAPI 的请求校验错误处理器，返回 400 和中文说明。兜底 500 用 http 中间件实现，并且要先于 CORS 中间件注册，否则跨域时浏览器读不到错误内容 | 2026-09-30 |
| 空查询参数 | `?testId=` 这种空值在 FastAPI 里声明成 `int | None` 会报校验错误，列表参数都按字符串接收再自己转换 | 2026-09-30 |
| 启动和停止 k6 | 用 `start_new_session=True` 把 k6 放进独立会话，信号只由服务发一次：k6 收到第二次中断信号会强制退出且不写 summary。停止只发一次 SIGINT，30 秒不退才强杀 | 2026-09-30 |
| 服务重启后的恢复 | 启动时把库里仍是"运行中"的记录标记为出错；遗留的 k6 进程按进程号加命令行里的 runId 识别后停掉（进程号会被复用，所以要同时比对命令行） | 2026-09-30 |
| 并发控制 | 同一时间只允许 1 个运行。用一把锁串行化"检查是否有运行 → 写库 → 启动"；等待线程出任何异常都兜底把状态改为结束，否则会永久挡住后续运行 | 2026-09-30 |
| 文件写入 | 回写 `run-record.json` 用临时文件加 `os.replace`，避免读到半截；`k6.log` 以追加方式打开；返回还在增长的 `k6.log` 时一次读完再响应 | 2026-09-30 |
| 运行进度 | 读 `k6.log` 末尾 4 KB，按回车和换行切分，取最新一行 `running (...)` 放进运行对象的 `progress` 字段 | 2026-09-30 |
| 单页应用托管 | 后端托管 `web/dist`；`/api/*` 找不到时永远返回 JSON 404；其余路径找不到文件时回退到 `index.html`；`/assets/` 下找不到就 404；用 `resolve()` 加 `is_relative_to()` 防目录穿越 | 2026-09-30 |
| 用假 k6 验证编排 | 开发后端时不对外发请求：用一个 shell 脚本冒充 k6，按环境变量决定睡多久、退出码是多少、写什么样的 `run-record.json`，把各个判定分支走一遍 | 2026-09-30 |
| 表结构迁移 | 版本记在 `PRAGMA user_version`，旧库启动时逐级迁移。SQLite 不能直接改列约束（如去掉 NOT NULL），只能重建表：建新表 → `INSERT … SELECT` → 删旧表 → 改名 | 2026-09-30 |
| 重建表要保住自增计数 | 重建后的自增计数会变成现存的最大 id，删过的最大 id 会被复用，历史运行里的 `envId` 就会指向另一个环境。迁移前读出 `sqlite_sequence` 的值，改名后写回 | 2026-09-30 |
| 迁移放进一个事务 | SQLite 的建表、改表语句和 `PRAGMA user_version` 都能回滚。Python 的 `sqlite3` 默认不为这类语句开事务，所以迁移用 `isolation_level=None` 的连接，自己写 `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK`；`executescript` 会先隐式提交，迁移里不能用。实测：迁移中途抛异常，库保持旧版本、数据原样 | 2026-09-30 |
| 迁移前备份 | 用 `Connection.backup()` 备份到 `data/app.db.v<旧版本>.bak`（已存在时不覆盖）。WAL 模式下直接拷主文件可能漏掉还没合并的内容，备份接口不会。迁移后不能直接回退到旧代码，要先用备份还原 | 2026-09-30 |
| 按结构判断是否迁移 | 除了看版本号，还看 `environments` 有没有 `type` 列，版本号没来得及写的库也能正确处理 | 2026-09-30 |
| 只读打开 WAL 库 | 只读连接也会在库文件旁边生成 `-shm` / `-wal` 文件，属于正常现象，主文件不会被改 | 2026-09-30 |
| 执行机信息采集 | 只用标准库，不加依赖：`/proc/meminfo`、`/etc/os-release`、`os.getloadavg()`、`shutil.disk_usage()`、`platform`。内存占用用 `MemAvailable` 而不是 `MemFree`（后者不含可回收的缓存）。取不到的字段返回 null，不让接口报错 | 2026-09-30 |
| CPU 占用的算法 | 取 `/proc/stat` 第一行相邻两次读数的差：`(总 − 空闲 − iowait) / 总`，是整机所有核合计的百分比 | 2026-09-30 |
| 取本机 IP | 对一个 UDP 套接字 `connect` 到文档保留网段 `192.0.2.1`，再看 `getsockname()`；不发任何包。比 `gethostbyname(hostname)` 可靠（后者常得到 `127.0.1.1`） | 2026-09-30 |
| 运行期间的采样线程 | 生命周期包在等待 k6 退出的线程里：那里启动，k6 一退出就停。间隔用 `Event.wait(1)`，停止时立刻醒来；只累计和、最大值、次数，不存每个样本；每一步都包了异常，采样出错不影响收尾。不到 1 秒的运行没有样本 | 2026-09-30 |
| 验证线程是否结束 | Python 3.12 的线程名不会同步到系统层，`/proc/<pid>/task/*/comm` 里看不到，要用 `Thread.is_alive()` | 2026-09-30 |
| 版本 2 → 3 的迁移 | 只是加表加列：`CREATE TABLE folders` 和 `ALTER TABLE apis ADD COLUMN folder_id`，都能放在同一个事务里；仍按结构判断（`apis` 没有 `folder_id` 列就迁移），备份到 `app.db.v2.bak`。全新的库由 `_SCHEMA` 直接建成最新结构，所以两处 DDL 要同时改 | 2026-10-09 |
| PUT 时把路径里的 id 注入请求体 | 文件夹不能放到自己或子孙下面，校验器要知道正在改哪一条；通用的 `replace_item` 在校验前把 `item_id` 作为 `id` 并进 payload，校验器本来就忽略多余字段，其他资源不受影响 | 2026-10-09 |
| 在真实库的拷贝上验证迁移 | 验证迁移时不碰正式库：从只读连接用备份接口把库拷到临时目录，新代码换端口、配合假 k6 启动，核对行数和逐列的值 | 2026-09-30 |
| 调试与运行互斥 | 复用 `runs.py` 的 `_start_lock`：调试在锁内确认没有运行、没有别的调试，占住模块变量 `_debug_busy`；`create_run` 在锁内检查这个变量。同一时间只允许 1 个调试，后来的直接 409 不排队（调试最长 90 秒，排队会让人以为卡死） | 2026-10-09 |
| 调试同步执行 | 路由是普通 `def`，FastAPI 放进线程池；`proc.wait(timeout=90)` 只阻塞那一个线程。超时先 SIGINT 再等 10 秒 SIGKILL，返回 500 | 2026-10-09 |
| 调试目录 | `results/_debug/<debugId>/`，`finally` 里整个删掉；服务启动时清理上次遗留的。产物接口的 runId 正则匹配不到 `_debug`，运行列表来自库，互不影响 | 2026-10-09 |
| 500 的 details 放日志 | `DEBUG_FAILED` 的 `details` 是 `k6.log` 的最后 30 行；JSON 格式的日志行转成 `[level] msg：error` 的样子。前端对这个 code 用等宽文本整块显示，其他错误逐条列出 | 2026-10-09 |
| 用本机小目标做端到端 | 一个标准库 `http.server` 脚本（JSON、POST 回显、302、PNG、4 秒慢响应、404）放在临时目录，配合第二个后端实例（换 `DATA_DIR` / `RESULTS_DIR`、端口 8099）把变量传递、提取、跳过、409、500 都走到，不动正式库也几乎不碰百度 | 2026-10-09 |

|---|---|---|
| 多 agent 并行 | 先写好三方接口契约（`docs/plans/mvp-contract.md`），再让执行引擎、后端、前端三个 agent 并行开发，各自只改自己的目录，由主会话统一联调和提交 | 2026-09-30 |
