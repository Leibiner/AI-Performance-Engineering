# ADR-005：MVP —— 可维护的管理控制台、数据驱动的流程、Python 后端、SQLite

- 状态：**Accepted**（2026-09-30 由用户确认，MVP 已按此实现）
- 日期：2026-09-30
- 相关：`plans/mvp-plan.md`、`plans/mvp-contract.md`、`records/tech-notes.md`、`ARCHITECTURE.md` §1.2、§3、§5、§8
- 对已有 ADR 的影响：**取代 ADR-004 的"只读"原则和技术选型**；**修订 ADR-003 的工具语言、存储、目标系统**；修订 ADR-002 中"流程是 JS 代码"的前提；ADR-001 的方向和对 AI 的约束不变。逐项说明见下文"对已有 ADR 的影响"。

---

## Context

Phase 0 的设计是：业务流程是手写的 JS 模块，放在 git 里；运行从命令行 `tools/run.mjs` 发起；Phase 1 只生成静态报告，Phase 2 才做一个**只读**的 Web 控制台（ADR-004）；外部工具用 Node.js 标准库，结果存 JSON 文件（ADR-003）。

2026-09-30 用户提出要先做出一个能在浏览器里使用的最小可用版本，并确认了以下要求：

1. 接口、业务流程、负载配置、验收标准、环境都要能在页面上增删改；
2. 要能从页面发起和停止压测，查看结果，历史自动存档；
3. 环境和依赖用 uv 管理；
4. 存储用 SQLite 单文件；
5. 前端用 Vue 3 + TypeScript + Vite + Element Plus + ECharts；
6. 禁止过度测试：不写单元测试套件，靠真实运行验证。

环境上的约束：本机没有 Docker 和 sudo，原定的目标系统 QuickPizza 起不来；系统自带的 Node 是已停止维护的 v18。

这些要求与 ADR-004 的"只读"、"定义走 git"、"页面不自建执行器"直接冲突，也改变了 ADR-003 的工具语言和存储。

## Options

### Option A：按原设计继续

命令行入口 + 手写 JS 的 Flow 模块 + 静态报告；只读控制台留到 Phase 2。

- 优点：定义在 git 里，有审核和版本；执行路径只有一条；流程有完整的代码表达力。
- 缺点：不满足用户"在页面上维护和发起"的要求；不会写 JS 的人无法维护流程。

### Option B：管理控制台，但定义仍在 git，页面只触发 CI

即 ADR-004 里的 F3：页面只是调用 CI 的触发接口，由 CI 执行命令行入口。

- 优点：保留 git 审核和单一执行路径。
- 缺点：页面上改不了定义；需要先有 CI 流水线、登录和权限，而 CI 平台至今未决；做不出"今天就能用"的最小版本。

### Option C：管理控制台 + 数据驱动的流程 + 后端直接编排 k6

定义存数据库，在页面上维护；后端在发起运行时把定义展开成一份 plan，启动 k6 子进程；一个通用的 k6 脚本读取 plan 解释执行。

- 优点：满足全部要求；一个进程、一个数据库文件就能运行；业务与负载分离、SLO 生成阈值、`invalid` 与 `failed` 的区分都能原样保留。
- 缺点：见 Consequences。

## Decision

**采用 Option C。**

| # | 决定 |
|---|---|
| 1 | 前端是**可维护的管理控制台**：接口、业务流程、负载配置、验收标准、环境都在页面上增删改；能从页面发起和停止压测；查看结果；历史存档 |
| 2 | 业务流程是**页面上维护的数据**，存 SQLite，由一个通用 k6 脚本（`perf/runner.js`）解释执行，不再是手写的 JS 模块 |
| 3 | 环境和依赖用 **uv** 管理，所以后端是 **Python 3.12 + FastAPI + 标准库 `sqlite3`**。前端依赖仍用 npm；Node 只用于构建前端 |
| 4 | 存储用 **SQLite 单文件** `data/app.db`（定义和运行），运行产物放在 `results/<runId>/` |
| 5 | 前端技术栈：**Vue 3 + TypeScript + Vite + Element Plus + ECharts** |
| 6 | MVP 的压测目标是 `https://www.baidu.com`，**只允许冒烟级别流量**：环境上设硬性上限（2 并发、每秒 2 次、60 秒），后端预检强制执行，不得调高 |
| 7 | **禁止过度测试**：不写单元测试套件，不引入测试框架，靠真实运行验证 |
| 8 | 三部分（`perf/`、`server/`、`web/`）之间的接口以 `plans/mvp-contract.md` 为唯一约定；改接口先改契约 |

**保留不变的核心设计**：

- 业务（接口、流程）与负载（负载配置）分开维护，只在发起运行时组装；
- 负载模型显式区分 open / closed；
- SLO 是数据，阈值由它生成，并自动附加有效性阈值；
- 判定为 `passed / failed / invalid / error / aborted`，`invalid` 优先于 `failed`，由确定性规则计算；
- 每次运行有 runId、完整记录和发起时的配置快照；
- 前端和 Grafana 都不计算判定；
- AI 的所有约束不变：不决定判定，不在 k6 运行路径中，不发起压测。目前没有任何 AI 功能。

### 对已有 ADR 的影响

**ADR-004（前端）——以下部分被取代：**

| ADR-004 的内容 | 现在 |

| 约束 1：前端和 API 只读，不写 Run Record，不调用 k6 | 后端提供增删改接口，启动和停止 k6，补全并保存 Run Record |
| 约束 2：只通过只读 API 访问；契约是 `schemas/run-record.schema.json` | 契约是 `plans/mvp-contract.md`，没有 JSON Schema 文件 |
| 约束 4：SLO、Profile、Flow、基线的修改始终走 git 和 PR | 定义在页面上修改，存数据库（基线尚未实现，存储形态待定） |
| 约束 5：前端和 API 可以整体移除，执行和判定不受影响 | 后端是运行路径的一部分，不能移除 |
| 约束 6 中的 `tools/` | 没有 `tools/` 目录 |

ADR-004 中**仍然有效**的部分：前端不计算判定和回归；不重画时序监控大盘（运行详情页的柱状图只画 Run Record 里的汇总数值）；`invalid` 与 `failed` 在界面上必须明确区分；F2（趋势、证据视图）和 F4（AI 建议面板，需先通过评估）仍是规划；npm 和构建步骤不进入 `perf/`。

**ADR-003（技术基线）——以下部分被修订：**

| ADR-003 的内容 | 现在 |
|---|---|
| k6 外部工具：Node.js，仅标准库 | 没有 Node 工具；后端是 Python 3.12 + FastAPI + uvicorn，依赖由 uv 管理 |
| 前端与只读 API 允许 npm 和构建，限 `web/`、`server/` | npm 和构建只在 `web/`；`server/` 是 Python |
| TypeScript：暂不采用 | 前端用 TypeScript（`vue-tsc` 做类型检查）；`perf/` 仍是原生 JS ES Module |
| 运行结果存储：`results/` 下的 JSON 文件，基线文件纳入 git，无需数据库 | SQLite 单文件 + `results/<runId>/` 产物；都不入 git |
| Phase 1 目标系统：QuickPizza | MVP 目标是百度，仅冒烟；QuickPizza 因本机没有 Docker 和 sudo 未采用。自有的目标系统未决 |
| 当前开发环境：未安装 k6 | k6 v2.3.0 和 Node v24.21.0 由 `scripts/setup.sh` 下载到 `.tools/` |

ADR-003 中**仍然有效**的部分：k6 v2.x 并固定 minor 版本（现为 v2.3.0），版本写入 Run Record；`perf/` 用原生 JS ES Module、无构建；默认不使用扩展；禁用清单；断言用 `check` + 阈值；OpenTelemetry Demo 作为 Phase 2–3 目标系统的候选。

**ADR-002（核心模型）：**

- 决定 2 的分层不变，但 Service 和 Flow 从 JS 模块变成了数据（接口、业务流程）。ADR-002 曾以"业务流程需要分支与提取"为由拒绝"用 DSL 描述 Flow"；现在接受了这个代价：提取用 `extracts` 实现，分支没有；
- 决定 4（强度与形状分离）**没有实现**：负载配置里直接写绝对数值；
- 决定 3 中"closed 需写明理由"靠约定，代码不强制；
- 决定 6 中 SLO 目前只到测试级别，还不能按流程 / 步骤设置；
- 决定 7 的判定规则不变，实现上分成两步：`perf/core/summary.js` 按阈值类别得出 `k6Verdict`，`server/runs.py` 结合退出码和停止请求得出最终判定；
- 决定 8（数据选择规则）尚无使用场景，因为还没有数据集。

**ADR-001（架构方向）：** Architecture First 和对 AI 的约束不变。Option B（Platform First）清单里的 Web UI、服务端、数据库三项现在以最小形态采用（单进程、单文件数据库）；插件系统、分布式控制器、Observability 平台、Agent Runtime 仍然不做。ADR-001 的复议条件 4（项目目标从"工程框架"变为"产品 / 平台"）部分成立：项目现在有了一个要维护的控制台，这是用户的明确选择。

## Why

- **用户要的是今天能在浏览器里用的版本。** Option A、B 都做不到"在页面上维护并发起"。
- **页面维护决定了流程必须是数据。** 定义既然存在数据库里，就不可能是手写的 JS 文件。一个通用脚本加一份自包含的 plan，是"数据驱动"最简单的实现：k6 要求 scenario 的 `exec` 指向导出的函数名，所以只导出一个函数，再用 scenario 名找回对应的流程。
- **uv 决定了后端语言。** 用户要求用 uv 管理环境和依赖，后端就是 Python。Python 标准库自带 `sqlite3`，后端只需要 FastAPI 和 uvicorn 两个依赖。系统自带的 Node v18 已停止维护，也不适合作为后端运行时。
- **SQLite 对当前规模足够。** 单机、单进程、同一时间 1 个运行，没有并发写入的压力；不需要部署和运维；备份就是复制一个文件。
- **百度只是"能跑通"的目标。** 本机没有 Docker 和 sudo，起不了自己的目标系统。用一个公开站点验证主流程，同时用硬性上限保证流量只到冒烟级别。
- **核心设计与"定义存在哪里"无关。** 业务与负载分离、显式模型、SLO 生成阈值、`invalid` 与 `failed` 的区分、Run Record，这些在数据驱动的模型下都能原样落地，所以保留。

## Consequences

正面：

- 有了可运行的端到端闭环：页面维护 → 预检 → 执行 → 判定 → 查看 → 存档；
- 不会写 JS 的人也能维护接口和流程；
- 多流程按权重混合（原 Phase 2 的 Flow Mix）提前实现；
- 实测确认了两个研究阶段未验证的事实：k6 v2.3.0 的 `handleSummary` 数据结构；k6 实时仪表盘在有浏览器连接时会阻止 k6 退出（`records/tech-notes.md`）。

负面 / 需要承担：

**1. 页面能发起压测，带来误加压的风险。**

现有护栏：

- **环境流量上限**：每个环境必填最大并发、最大到达率、最长时长；发起运行时后端预检，超过即拒绝（422）；
- **同时只允许 1 个运行**：不会叠加负载（409）；
- 引擎侧：`gracefulStop` 收紧到 5 秒；到达率模型不自动扩容；某一步失败后本次迭代不再继续，但仍等待 think time。

**没有的护栏**：

- **没有登录、权限和审计**。服务监听 `0.0.0.0:8088`，跨域全部放行。能访问这个端口的人都可以修改定义、发起运行；
- **环境上限本身可以在页面上修改**。"百度环境不得调高上限"目前只靠约定，代码不阻止；
- **没有目标白名单**。任何合法的 http / https 地址都能建成环境；
- 没有失控自动中止，没有运行之间的冷却时间。

所以这个控制台只适合在可信的内网里单人或小范围使用。

**2. 定义存数据库后，不再经过 git 审核。**

- 改接口、流程、负载配置、验收标准、环境上限都没有 PR、diff 和修改历史，只有 `updatedAt`；
- 能追溯的只有每次运行的配置快照：可以知道"这次跑的是什么"，不能知道"谁在什么时候改了什么"；
- `data/app.db` 不入 git，备份靠复制文件；
- 种子数据在 `server/seed.py` 里（入 git），只在全新的库里写入一次。

**3. 数据驱动的流程表达力有限。**

- 只能表达**按顺序执行的步骤**：没有分支、循环、轮询、条件判断；
- 变量只在一次迭代内有效，不能跨迭代缓存（例如登录一次、复用 token）；
- 没有数据集、账户池、唯一键；
- 检查只有三种：期望状态码、期望包含的文本、变量提取成功；没有业务指标；
- 只支持 HTTP。新增协议要同时改数据模型、页面表单和解释器。

**4. 后端成了运行路径的一部分。**

- 后端不能移除；只能单进程运行（k6 进程句柄在内存里）；服务重启会中止正在进行的运行；
- 判定规则分在两处：`perf/core/summary.js`（JS）和 `server/runs.py`（Python）；
- 没有命令行入口，**CI 的接入方式要重新设计**（`ARCHITECTURE.md` §3.8）。

**5. 其他代价。**

- 两套工具链：Python（uv）和 Node（npm，只用于构建前端）；
- 对百度只能冒烟，**不产生任何性能结论**；压力、尖峰等负载无法真实运行；
- 没有凭据管理：环境和接口的请求头明文存库，并进入快照和产物；
- 没有静态报告，看结果需要服务在线（产物文件仍可单独打开）；
- 不写单元测试套件意味着判定逻辑没有自动化的回归保护，改动后要靠真实运行和假 k6 重新验证。

## Reconsideration Conditions

以下任一条件出现时重新评估本 ADR 的对应部分：

| 条件 | 要做的事 |
|---|---|
| 服务要给多人使用，或要暴露到不可信的网络 | **先**做登录、权限和操作审计；环境上限的修改加保护；收紧跨域设置 |
| 要对自有系统做冒烟以上的测试 | 先有目标白名单或环境分级，区分"可以加压的环境"和"只能冒烟的环境" |
| 真实业务流程需要分支、循环、轮询，或需要数据集 | 评估两条路：扩展数据模型，或引入"手写 JS 模块"作为第二种流程类型（回到 ADR-002 的原设想） |
| 定义的改动需要审核和版本 | 评估把定义导出为文件纳入 git，或增加修改历史 |
| 需要多个运行同时进行，或多实例部署 | 重新设计运行编排（现在依赖内存里的进程句柄和固定的仪表盘端口）；SQLite 换成 PostgreSQL |
| 接入 CI | 先确定入口：调用后端接口，还是"plan 文件 + 命令行" |
| 需要离线报告或 CI 制品 | 重新评估静态报告 |
| 判定逻辑出现过回归，或改动变得频繁 | 由用户重新决定是否给 `summary.js` 和判定规则加自动化测试 |
| k6 修复了"实时仪表盘阻止退出"的行为 | 重新评估在运行详情页显示实时图表 |
