# ADR-006：测试数据与变量作用域 —— 扩展数据模型，不引入手写 JS

- 状态：**Accepted**（2026-10-10，用户要求"单接口、多接口上下游需要引用变量，或者需要 csv 等文件的引用时，如何解决……将项目完善"）
- 日期：2026-10-10
- 相关：`plans/mvp-contract.md` §3.1、§3.5、§3.6、§3.7、§4、§5；`ARCHITECTURE.md` §4.3；`records/tech-notes.md` §2
- 对已有 ADR 的影响：处理 **ADR-005 复议条件 3**（"真实业务流程需要分支、循环、轮询，或需要数据集"）中"需要数据集"这一半，选"扩展数据模型"；ADR-002 决定 8（数据选择只用 `*InTest` 字段）第一次有了使用场景，照它执行。分支、循环、轮询仍然不做。

---

## Context

MVP 的变量只有两层：被测环境的变量初始值，和一次迭代内步骤提取到的变量。实际使用中暴露出这些缺口（2026-10-10 四路调研：代码审计、两路业内做法调研、k6 v2.3.0 实测）：

1. **每次迭代都重新登录**。变量只活一次迭代，登录这种最重的接口被放大到和业务请求一样多，登录耗时还混进总体 SLO。
2. **没有数据集**。账号池、商品 ID 表、一次性的券码都表达不了；唯一键、幂等键也写不出来（没有动态变量）。
3. **上下游关系不可见**。保存和预检都不检查"引用的变量有没有来源"，未定义的 `{{token}}` 被原样发出，运行跑完才知道失败；流程试跑会注入浏览器里的当前值，出现"试跑通过、压测失败"。
4. **单接口调试依赖上游**时只能手动先调一次上游；上游和目标不在同一次 k6 运行里，靠 Cookie 维持的会话传不过去。
5. **请求体只有原始字符串**。表单和文件上传（multipart）都做不了。

## Options

### Option A：扩展数据模型（采用）

数据集、流程分段、流程变量、动态变量、表单与文件请求体都作为**数据**加进接口和流程的定义，仍由 `perf/core/interp.js` 解释执行。

- 优点：页面维护、调试与压测同一份代码、预检能静态检查变量来源，这些现有性质全部保留。
- 缺点：表达力仍然有限（没有分支和循环）；数据模型和页面表单变复杂。

### Option B：引入手写 JS 模块作为第二种流程类型

- 优点：表达力完整。
- 缺点：两条执行路径；变量来源无法静态分析；页面上维护不了；需要代码审核渠道（ADR-005 的定义不进 git）。

### Option C：前置脚本（类似 Postman 的 `pm.sendRequest`）

- 缺点：脚本让变量来源不可分析（Postman 自己也无法告诉用户变量由谁设置），本质上是 Option B 的半成品。不采用。

## Decision

采用 Option A，具体是以下 7 条：

| # | 决定 |
|---|---|
| 1 | **变量按求值顺序分层，后写的覆盖先写的**：被测环境变量 → 数据集的行 → 流程变量 → 初始化段的输出 → 步骤提取。`{{$名称}}` 是内置的动态变量，独立命名空间，用户不能定义 `$` 开头的变量 |
| 2 | **数据集**是独立资源：后端把 CSV 解析成规范的行（UTF-8，表头即变量名），绑定在**业务流程**上，每个绑定有取行方式（按顺序 / 随机 / 每个 VU 固定一行）和数据用完时的处理（循环使用 / 停止测试）。负载配置里不放任何数据设置 |
| 3 | **流程分段**：业务流程分"初始化（每个 VU 一次）"和"每次迭代"两段。初始化段的输出在这个 VU 的后续迭代里保留；可设重新初始化的间隔。这是生命周期结构，不是分支：执行次数由阶段决定，与响应内容无关 |
| 4 | 初始化段的请求带 `phase:init` tag，**不计入**总体指标和 SLO 阈值，只出现在分步骤指标里（`ARCHITECTURE.md` §4.3 原有的规划："登录与业务 SLO 分开"） |
| 5 | **数据用完时的"停止测试"判 `invalid`**：用计数指标 `data_exhausted` 加一条 validity 阈值（`abortOnFail`），k6 以 99 退出。不用 `test.abort()`（会被判成 `aborted`，看起来像有人点了停止） |
| 6 | **变量来源在预检里静态检查**：正式运行和流程试跑都按"环境 + 数据集 + 流程变量 + 前面步骤的提取 + 动态变量"检查每个引用，没有来源就拒绝。流程试跑不再注入浏览器里的当前值，和正式运行语义一致；当前值只用于调试单个接口 |
| 7 | **单接口调试可以先跑上游接口**：上游和目标放在同一次 k6 迭代里（同一个 VU、同一个 Cookie 罐）。这只是调试时的依赖解析，正式运行绝不自动插入步骤 |

实现上的硬约束（k6 v2.3.0 实测，见 `records/tech-notes.md` §2）：

- 数据集写成单独的 JSON 文件放进运行目录，引擎用 `SharedArray` 加载；**不内嵌进 plan**（plan 会被每个 VU 各解析一次，5 万行数据在 5 个 VU 下内存从约 140 MB 涨到约 420 MB）。
- CSV 只在后端用 Python 解析（`utf-8-sig`，失败再试 `gb18030`）：k6 没有非 experimental 的 CSV 模块，引擎里也解不了 GBK。
- 取行只用 `exec.scenario.iterationInTest` 和 `exec.vu.idInTest`（ADR-002 决定 8）。`iterationInTest` 按 scenario 各自从 0 开始，所以多个流程按顺序共用一个数据集时，由后端分配步长和偏移。
- multipart 请求体由引擎手工拼装：k6 的对象写法字段顺序随机，且合并进来的 `Content-Type` 会丢掉 boundary。
- 后端启动 k6 一律带 `K6_AUTO_EXTENSION_RESOLUTION=false`：k6 v2.3.0 遇到未知的 import 默认会联网向 Grafana 的构建服务请求下载扩展。

## Consequences

正面：

- 账号池（每个 VU 固定一行 + 初始化段登录）、一次性数据（按顺序 + 停止测试）、唯一键（动态变量）都能在页面上表达；
- 登录不再被放大，也不再污染业务 SLO；
- "试跑通过、压测失败"的一类问题在预检阶段就被拦住。

负面 / 需要承担：

- 每次运行把用到的数据集和文件复制进运行目录（`datasets/`、`files/`），占用磁盘；它们不经产物接口提供，产物仍然只有 5 个文件名；
- 文件上传的内存约为"文件大小 ×（VU 数 + 2）"，预检按此设上限；
- 数据集按流程绑定，没有"按被测环境切换数据集"（测试环境和生产环境的账号不同时，要建两个流程，或用环境变量）；
- 初始化段的 token 过期只能靠"重新初始化间隔"处理，没有"遇到 401 就重新登录"；
- 环境变量里的密码仍然明文存库并进入快照（ADR-005 已登记的凭据问题，本 ADR 不处理）。

## Reconsideration Conditions

| 条件 | 要做的事 |
|---|---|
| 需要按被测环境切换数据集 | 在流程的数据集绑定上加"环境 → 数据集"的覆盖映射（要求列一致） |
| token 过期时间短于测试时长且不固定 | 评估"本迭代出现 401 → 下次迭代重新初始化"这个固定选项 |
| 需要分支、循环、轮询 | 仍按 ADR-005 复议条件 3 评估，本 ADR 不改变"不做分支和循环" |
| 数据集超过 10 MB 或 10 万行成为常态 | 评估分片加载，或在 k6 的 CSV 模块转正后改用它 |
